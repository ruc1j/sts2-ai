## 背景 1: ラボの仕組み（どの API で入場状態を作るか）

`run_official_bosslab.ps1` が 1 試行 1 プロセスでゲームを起動し、`BossLab.cs`（worktree
`official_mod/`、main ツリーの `official_mod/` は対照 run とハッシュ一致のまま）が
`--sts2ai-bosslab --bosslab-plan --bosslab-trial --bosslab-out` で:

1. `Player.CreateForNewRun(IRONCLAD, UnlockState.all)` → `RunState.CreateForNewRun(acts, seed=plan の
   run_seed[-offset])`（`RunState.cs:272`。`RunRngSet(seed)` は任意 seed 文字列可）→
   `RunManager.SetUpNewSingleplayer(state, shouldSave:false)`（`RunManager.cs:236`）。
2. `PreloadManager.LoadRunAssets/LoadActAssets` → `FinalizeStartingRelics` → `Launch()` →
   `NGame.Instance.RootSceneContainer.SetCurrentScene(NRun.Create(state))` → `SetActInternal(act 2)`。
   （`NSceneBootstrapper.cs:101-113` と `NGame.cs:1152` 相当の実行順。headless で動作確認済）
3. walked floors を `AppendToMapPointHistory` で埋めて（Act1 分 17 + Act2 分 15。ボス入室で 33 番目に
   なる）`ActFloor=16` を設定。ボスの敵生成 RNG `seed = runSeed + TotalFloor + hash(encounter.Id.Entry)`
   （`EncounterModel.cs:266-269`）が実走と同値になり、敵構成・初期 HP（321/320/318）・行動系列が
   再現される（T6a で突合済。18 行マップの 17/18 仕様も `history_per_act` で吸収）。
4. `ApplyPlayerState`（BossLab.cs:268-320）: 開始レリック除去→`RelicModel.FromSerializable`+
   `AddRelicInternal`、ポーション→`PotionModel.FromSerializable`+`AddPotionInternal`（枠 3 初期は
   `Player.cs:28 initialMaxPotionSlotCount=3`。注入 10/10 完全一致検証済）、デッキ→`Clear` 後に全枚
   `player.RunState.LoadCard(SerializableCard, player)`→`Deck.AddInternal`、`SetMaxHpInternal`/
   `SetCurrentHpInternal`（`Creature.cs:488-493`）。
5. `RunManager.EnterRoomDebug(RoomType.Boss, Unassigned, encounterMutable)`（`RunManager.cs:990`。
   room type は encounter 側へ上書き 995-997。入室前に ClearScreens+ExitCurrentRooms 1012-1050）で
   即ボスへ。戦闘開始の山札シャッフルは `PopulateCombatState`→`RandomizeOrderInternal`
   （`Player.cs:802-811`、`CardPile.cs:69`）、RNG は `RunState.Rng.Shuffle`（`CombatManager.cs:370`、
   カテゴリ seed は `RunRngSet.cs:107-118`）。Fisher-Yates で一様（`ListExtensions.cs:45-63`、
   「unstable」＝入力順に依存と文書化: 1 枚追加で全カードの並びが混ざる。arm 間で対称）。
6. 進行は `CombatBridge.Run(CancellationToken.None)` を BossLab が直接並走起動（AutoSlay 非起動でも
   agent bridge が動く。修正 2 由来）。勝敗の一次情報は bridge が `--bridge-trace` に書く
   `combat_end`（`CombatBridge.cs:215` の `won = hp>0 && !gameOver`）を読み、敵残 HP・ターン数は
   参考値（200ms ポーリングで撃破瞬間を取り逃がすため判定に使わない。`outcome_source` で区別）。
7. 1 試行の結果行（won・entry/final HP・敵残 HP・turns・elapsed・seed）を JSONL に追記して
   `NGame.Instance.GetTree().Quit(0)`。runner は per-trial の observation/action/trace/log を
   `data/bosslab_*/trial_XXXX_*` に分離し `lab_meta.json` に plan/dll/agent/runner の sha256 を記録。
   起動時に「ゲーム起動中」「mods/Sts2Ai 残り」を ANOMALY として拒否。

## 背景 2: 実機試験で見つけた不具合と直し方（worktree に入れてあり、この草稿はそれらを壊さない）

1. Owner なし NRE: `CardModel.FromSerializable` だけだと Owner が null で、`EnterRoomDebug` 内の
   `RunState.Contains(model)` が参照外し。→ `player.RunState.LoadCard(serializableCard, player)`
   で生成してから `Deck.AddInternal` に変更（leader 修正・BossLab.cs:299-307 注释に残す）。
2. 戦闘が誰も打たない: lab は AutoSlay を起動しないため `CombatRoomHandler` patch が発火せず、
   入力なしで 300s タイムアウト。→ `EnterRoomDebug` 後に `CombatBridge.Run(CancellationToken.None)`
   を BossLab が自分で並走起動（修正 3・BossLab.cs:146）。
3. 手札選択カードで停止: AutoSlay が全 run 向けに張っていた `CardSelectCmd.UseSelector(new
   AutoSlayCardSelector(rng))` のスコープが lab に無く、Burning Pact 等で戦闘が停止（pass1 初期の
   3 試行が 200s タイムアウト）。→ `BossLab.RunTrial` で `EnterRoomDebug` の前に UseSelector
   スコープを張る（leader 修正）。
4. PowerShell 構文: `Set-Content -Value (ConvertTo-Json … + 改行)` の `+` が引数扱いになる失误で
   初回 runner が落ちた。→ 括弧でグループ化（leader 修正）。
5. 勝敗判定の修正（dsh）: 敵 HP の 200ms サンプル最終値で勝敗を determinate していた初期実装は
   撃破瞬間を取り逃がすと勝ちを誤って敗北にしていた。→ `combat_end` レコード由来に変更し、
   レコードが無い試行のみ player HP>0 fallback（`outcome_source` に区別を記録）。

## 背景 3: 忠実性（何を一致させ、何を割り切ったか）

一致確認済み（同一 entry に対して実走トレースと lab 先頭観測の突合、T4a/T6a/T8c、wins run の
ターン別突合で更新: `bosslab_turn_diff_wins.md`）: 入場 HP/最大/energy/block・レリック ID 集合・
relic_counters（trace 露出分）・ポーション（個数 ID 枠順 10/10）・敵初期 HP と行動系列と intent 数値
（Bite 28/14(colossus 半減)/30、THRASH 8x2→10x2→12x2、salivate +2 増分）・sim 予算 100・
デッキ多重集合（ID・強化）と手札/山札枚数。spec 抽出は元トレースと完全一致。

不一致と対処:
- EMBER_TEA（と同一族の STONE_CALENDAR 1 件）: FromSerializable がデフォルト状態で新生成するため、
  使い切り counter の入室時効果（+2 Strength）が lab だけ再発動。実走は Combats を消費済みで
  power なし。trace の relic_counters に该 counter が出ないため抽出フィルタで拾えず、この 2 レリック
  保有 spec を実験から除外（4 件）。根本復元（SerializableRelic.Props への注入 + bridge 側の counter
  露出）は保留中（優先度 lowered、leader 判断）。STRIKE_DUMMY 等「run 横断の暗黙状態（Props）」系は
  lab では空で再生成され、wins run で dummy 含む 4 trial は 2 勝 2 敗（勝利を止めていないことを確認）。
- enchantment・カードの成長 vars・入場時 power・relic counter を持つ入場状態は v1 の注入で
  扱えないため全実験の選択条件で除外（この条件自体が雪崩前=高HP勝利状態を減らす選択バイアス:
  クリーン 69 の実走勝率は 20%(14/69)、band >=80 でも 25 件中 7 勝。母集団 40% との差はこの
  フィルタで説明がつく）。
- 戦闘開始のシャッフルと引く順は一致させない（Shuffle stream の位置が lab は 0・実走は先行消費
  済み。分散要因で arm 間対称）。入場順の完全再現を入れるなら `CardPile.RandomizeOrderInternal` の
  patch か save 復元案（`RunState.cs:291 FromSerializable`）が必要。

## 背景 4: pass1 が 0/36 だった理由と A の −33pt が再現しなかった事実

pass1（3arm ±Shrug 予備実験）の 36/36 全敗は計器故障ではない。理由は (i) 選択バイアス—選定 6 spec
は「クリーン∩Shrug 保有∩実走敗北」の床近く集合で、記録母集団の勝率 40% ではなく床付近 (ii) 床効果
—base が全敗の entry 集合では arm 差が勝利方向へ動かせない。同一 entry の実走削り中央値平均 0.655
に対し lab base 0.551（+0.12±0.06 SE、2SE 示唆）は pass1 の selection と policy 差分（元 run 群は
