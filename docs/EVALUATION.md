# 評価基準

2026-10-05改訂。実験を計画し、変更の採否を判断するときの基準とする。README、CODEWIKI、Obsidianに残る旧基準と矛盾する場合は、この文書を優先する。過去の測定値と当時の採否は履歴として残す。

最終目標はAct 3踏破率を上げること。**ゲーム再現の正しさ、個別の判断の改善、エージェント全体の強さを別々に評価する。** 「3 seed以上で改善」「3 decisions以上で分岐」を一律の採用条件にはしない。まず次の判定表と実験手順を読み、記録時は末尾の書式を使う。

## 変更の種類ごとに採用根拠を分ける

| 評価対象 | 必要な証拠 | 判定 |
| --- | --- | --- |
| ゲーム再現の正しさ | 対象バージョンのゲーム実装・実観測との照合、最小の回帰テスト、全テスト成功 | 確認できた修正を「正しさとして採用」。踏破率への効果は別記する |
| 個別の判断の改善 | 対象場面での旧版・候補版の比較、判断から結果に至る記録、悪化例の確認 | 「局所改善」「局所悪化」「差を検出せず」「未測定」を記録。これだけで全体への採用を決めない |
| エージェント全体の強さ | 事前に固定したseed集合での実走比較と、調整に使っていないseed集合での確認 | 下記の指標と採用条件で「採用」「保留」「不採用」を決める |

評価関数の重みやカード優先順位の変更は戦略の変更である。もっともらしい説明や回帰テストの成功だけで「正しさの修正」に分類しない。仕様の修正と戦略の変更が混ざる場合は分けて検証する。正しいモデルで成績が落ちた場合は、その事実を残し、モデルに依存する戦略を調べる。例外、違法行動、通信障害を新たに起こす修正は解消するまで採用しない。

## 主指標は踏破率、戦闘勝利数は補助指標とする

全体比較の単位はseedごとのrunとし、各seedの重みを等しくする。標準は各seed・各版1 run。反復する場合は全seed・両版で回数を揃え、到達点は同じ反復番号どうしで比較してseedごとに平均する。同じrunの多数の判断を独立した試行として数えない。

1. 主指標はAct 3踏破数／結果が確定したrun数。計画したrun数、完了数、不明数も併記する。
2. 途中の改善はAct 2突破率、Act 1突破率、到達点の順に見る。到達点は同じseedの旧版と候補版をAct番号、Act内floorの順で比較し、改善・悪化・同値を数える。floor表記はログの定義を揃える。
3. 戦闘勝利数、被ダメージ、ボス開始HP、ボス残HPは原因調査に使う。戦闘数は経路で変わるため、合計勝数の増加を踏破率の向上と呼ばない。ボス残HPの直接比較は同じボス・開始状態で行う。条件が違えば参考値とする。

Act 3踏破は当該runの新しいresultの`act_3_complete: true`と最終戦ログで確認する。死亡はtraceの`combat_end`にある`won=false`、`hp=0`で確認する。resultの欠落、途中終了、`terminal=true`だけでは踏破も敗北も確定しない。Act 1・2突破もログ等で確認し、不明を0に置き換えない。

## 局所検証と全体比較で母数を変える

局所検証では、対象の効果が実際に発生しうる場面を選んでよい。「状態にカードやpowerがある」「発動条件を満たす」「判断が変わる」「結果が改善する」を分けて数える。発動機会が0なら未測定、機会があって比較結果が同じなら、その範囲で差を検出せずとする。

全体比較では、対象場面が出なかったseedも含める。片方だけがレリックを買った場合も、戦略全体の結果として残す。両方で同じ効果が出たseedだけを選ぶと、経路や購入判断による差を落としてしまう。機構単独の因果を調べるときは、同じ観測から旧版と候補版を比較し、モデル内の予測と実ゲームの結果を区別する。

固定パネルを何度も見て調整した後は、そのパネルは開発用と扱う。未知のseedでの確認結果を見て再調整したら、その集合も開発用へ移す。同一seedの再走は再現性確認であり、独立したseed数には加えない。

## 実験の前に比較条件と終了条件を固定する

実験記録に次を埋めてから走らせる。既存の固定8 seedは開発用として使えるが、全体の強さを確認する集合を兼ねない。

- 仮説、変更の種類、対象場面、旧版と候補版のcommitおよびソース・Modのハッシュ。
- ゲームバージョン、キャラクター、難易度、userdataのスナップショット、探索回数と乱数条件。全戦闘でエージェントを使い、Act 3まで走らせる。
- 開発用と確認用のseed一覧、選定方法、各seedの反復数。確認用は候補の結果を知らずに選び、対象効果の出現や過去の勝利を条件にしない。
- 主指標、補助指標、予定run数、時間上限、再実行条件。結果を見て有利なseedだけ追加したり、勝った時点で打ち切ったりしない。

候補版は確認用の測定が終わるまで凍結する。旧版も同じ実行条件で測り直すか、条件とハッシュが揃った既存記録を使う。実験の出力先を分け、走行中のソースやModを変更しない。

外部要因のクラッシュや中断は未完了として別記し、同じseed・版・条件で別tagへ再実行する。全試行を残し、成功した試行だけを選ばない。候補版に起因する例外や停止は信頼性の悪化であり、母数から消して採用を通さない。原因不明の欠測や条件不一致が残る比較は保留する。時間上限に達したら、確定した結果と不足分を記録して保留する。

## 採用、保留、不採用を決める

戦略変更は、対象場面で意図した動作を確認し、開発用・確認用の両集合を計画どおり比較したうえで判定する。各集合について、まずAct 3踏破数の差を比較する。同値ならAct 2突破数、Act 1突破数、到達点の改善seed数から悪化seed数を引いた値の順に見る。最初の非ゼロの差が正なら改善、負なら悪化、すべて0なら同値とする。比較するrun数と反復数は両版で揃える。

- **採用**：開発用・確認用の両集合で改善し、未解消の信頼性の悪化がない。Act 3が同値で途中の指標だけが改善した場合は「到達度改善として採用、踏破率向上は未確認」と記す。
- **保留**：局所改善だけ、機会不足、欠測、集合間で結果が割れる、または同値。次に必要な証拠を具体的に書く。1 seedの改善でも再検証候補には残す。
- **不採用**：実装・前提の誤りが判明した、または開発用・確認用の両集合で悪化した。理由と対象範囲を残す。少数例だけで将来のあらゆる条件でも無効とは結論しない。

これは開発上の採否であり、統計的な有意差の保証ではない。「3 seedで改善」だけで一般的な勝率向上を証明したとは扱わない。報告は対象集合、踏破数／母数、各seedの増減を伴う観測結果とし、一般化する主張には別途、標本数と不確実性の検討を要する。既知の勝利seedが1本悪化したことだけで拒否する旧運用にも戻さない。

## 既存の結果を新基準で読み直す

CODEWIKIのRound 135にある`priceband`は、5 seed中1本の到達点がAct 3 Floor 5から15へ改善し、3本はレリック購入がなかった。新分類は「局所改善あり・全体採用は保留」。3本の非購入例も全体比較に残す。独立した確認用集合の証拠がないため、今回の改訂だけでmainへ取り込まない。

`ACT3_GOAL_20261005.md`のInflame購入は同一seedでの到達度改善、Hellraiser使用順は同じボス開始HPでの残HP改善として扱う。いずれも全体の踏破率向上は未確認。HP監査の一致は比較した項目の再現性を示し、未観測の効果や将来ターンを含むモデル全体の正しさは保証しない。

## 記録書式と既存ツール

実験ごとに以下を記録する。空欄は未確認と明示し、追加実験の対象を決める。

```text
仮説・変更の種類・対象場面:
旧版／候補版、ゲーム／Mod／userdata／探索条件:
開発用seed／確認用seed、選定方法、反復数:
予定run数／時間上限／再実行条件:
判定に使う指標（標準から変える場合は測定前に理由を記録）:
計画数／完了数／不明数／外部障害／候補由来の障害:
局所検証: 発動機会・判断差・結果差（件数とseed数）:
全体比較: 集合ごとのAct 3・2・1突破数／母数、到達点の改善・悪化・同値:
各seedの結果、悪化例、証拠ファイル:
採用／保留／不採用、その根拠と次に必要な証拠:
```

`python3 data/compare_panel.py <arm_tag> <control_tag> <arm_dir> <control_dir> <seed ...>`は生の戦闘成績とresultの値を調べる補助ツールである。採否や踏破率を自動判定しない。表示されるmechanicの共通出現は発動や因果の証明ではなく、カードIDの最初の差だけでは全行動の差も判定できない。

各runの完了確認には`python3 data/run_usability.py data/<tag>_<seed>_agent.jsonl data/<tag>_<seed>_mod.log`を併用する。これはファイル上の完了確認を助けるもので、例外の原因、版の一致、勝利の最終戦ログは別途確認する。生の集計をそのまま採用条件へ渡さない。
